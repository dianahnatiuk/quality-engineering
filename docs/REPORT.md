### 1.4 Архітектурно-математичне обґрунтування

**Порядкові оцінки не усереднюються.** Рейтинг безпеки Sonar `A…E` — це лише *впорядкування*: відстані між A і B, B і C не визначені й не рівні. Якщо закодувати A=1, C=3, середнє дорівнює 2, тобто «B». Але кодування довільне: з тим самим порядком A=1, B=2, C=10 середнє стає 5,5, і «середня оцінка» змінює зміст. Результат залежить від вибору чисел, а не від даних, тому це методологічна помилка. Для порядкових даних валідні мода, медіана (при парній кількості — лише нижнє/верхнє серединне значення), перцентилі та частоти. Для M2 звітуємо «найгірший клас» (max) і кількість знахідок у кожному класі.

**Чому p95, а не середнє.** Час відгуку має праве скошений розподіл із довгим хвостом: у нашому сервісі хвіст створюють retry з експоненційним backoff і timeout. Приклад: 100 запитів, 90 по 40 мс і 10 по 1500 мс (timeout+retry). Середнє = 0,9·40 + 0,1·1500 = **186 мс** < 250 мс, і Quality Gate показав би PASS, хоча кожен десятий користувач чекає 1,5 с. p95 = **1500 мс** (FAIL), що відображає реальний досвід; медіана (40 мс) хвіст ігнорує зовсім, тому для SLO потрібен саме верхній перцентиль. Окремо: p95 різних прогонів не можна усереднювати (перцентиль неадитивний) — треба об'єднувати сирі виміри або брати медіану p95 по прогонах.

**Інтервальна проти відносної.** В інтервальній шкалі (календарні дати, °C) нуль умовний, тому коректні різниці, але не відношення: «2026-11-01 удвічі пізніше за 2026-05-15» не має змісту. У відносній шкалі (мс, години, Cognitive Complexity, Σ рядків) є абсолютний нуль, тому допустимі відношення й усі статистики. Саме тому M5 (дата) — інтервальна, а M6 (різниця дат) — відносна.

**Медіана проти середнього.** Середнє арифметичне = сума / кількість, воно чутливе до викидів; медіана — значення, що ділить впорядкований ряд навпіл, і до викидів стійка. Наш приклад: середня Cognitive на метод впала з 2,4 (71/30) до 1,3 (56/42) здебільшого тому, що Extract Method збільшив кількість методів, а не лише через спрощення; жодне середнє не покаже «один метод зі складністю 25 серед простих». Тому gate для M1 будується на **максимумі** (і за потреби p90), а не на середньому чи медіані.

## Завдання 2. Закон Гудхарта та метрика-балансир

### 2.1 Аналітична декларація ризику

**Обрана метрика:** Line Coverage (%) модуля `lab2.resilience`. **Сценарій:** PM прив'язує бонуси команди до «покриття ≥ 90 %».

**Як команда «підженеться» під зелену зону.** Найдешевший шлях — тести без перевірок: `new ResilientPricingClient(...).getPrice("1")` для кожної гілки (успіх, retry→fallback, baseline) без жодного `assert`. Усі рядки виконуються — покриття 100 % — але тест не падає ні за яких змін поведінки (див. `src/test/java/lab5/CoverageGamingDemoTest.java`). Наслідки для коду:

- можна безкарно зламати `attempts <= cfg.maxRetries` (на одну спробу більше/менше) — тест зелений;
- можна видалити `sleeper.sleep(...)` (backoff зникає, залежність добивається «в упор») — зелений;
- можна повернути `cfg.fallbackPrice` без прапорця `degraded=true`, і споживач не дізнається про деградацію — зелений;
- результат: дашборд «98 % якості», а реальна здатність тестів ловити регресії у resilience-логіці близька до нуля, регресії доходять до production.

### 2.2 Специфікація метрики-балансира: Mutation Score

| Поле | Значення |
|---|---|
| Назва | **Mutation Score**, % = вбиті мутанти / усі мутанти × 100 |
| Призначення | Показує, чи **тести падають**, коли код навмисно псують (мутації: інверсія умов, `<=`→`<`, видалення виклику `sleeper.sleep`, підміна значень, `*=`→`/=`) |
| Інструмент | **Pitest** (`pitest-maven` + `pitest-junit5-plugin`), безкоштовний, звіт HTML/XML |
| Чому це балансир | Покриття міряє «чи виконано рядок», Mutation Score міряє «чи перевірено результат». Тест без assert виконує рядки, але не вбиває жодного мутанта, тому накрутка Coverage без реальних перевірок **не підвищує** Mutation Score. Підняти обидві цифри можна лише написавши справжні тести, тобто «хакінг» стає дорожчим за чесну роботу |
| Приклад вбивчого тесту | `sleeper` записує аргументи, `assertEquals(List.of(100L, 200L, 400L), slept)`; `assertEquals(4, result.attempts())`; `assertTrue(result.degraded())` |

### 2.3 Balanced Quality Gate

```
GATE_PASS  =  ( Line Coverage[lab2.resilience]  >= 80 % )
          AND ( Mutation Score[lab2.resilience] >= 65 % )
```

| Поріг | Обґрунтування |
|---|---|
| Coverage ≥ 80 % | Загальноприйнятий поріг Sonar «Clean as You Code» для нового коду; необхідна, але недостатня умова |
| Mutation Score ≥ 65 % | Нижня межа для логіки з бізнес-інваріантами; відсікає assert-less тести (їхній score — десяткові відсотки) і водночас досяжний без тестування тривіальних геттерів. Підлягає калібруванню за першим базовим прогоном (⟦baseline Pitest⟧) |
| Оператор AND | Дозвіл лише за балансу обох індикаторів; жодна метрика не може «компенсувати» іншу (на відміну від зваженої суми) |

Реалізація: JaCoCo (`check`, правило LINE ≥ 0.80) та Pitest (`mutationThreshold=65`) прив'язані до `verify`; збірка падає, якщо порушено будь-яку з умов, тобто PASS можливий лише за виконання обох. Конфіг: `scripts/lab5/pom-additions.xml`, запуск: `mvn clean verify`. Існуючий gate складності (`ComplexityMeter --fail-over`, Cognitive ≤ 15, Cyclomatic ≤ 10) залишається третьою незалежною умовою.

## Підготовка до усного захисту

- **Інтервальна vs відносна?** Інтервальна: є лише різниці (дати); відносна: є абсолютний нуль, тому ще й відношення (мс, години).
- **Чому не середнє для Security Rating?** Порядкова шкала: кодування довільне, середнє «A і C = B» залежить від вибору чисел.
- **Медіана vs середнє?** Медіана — центральне значення впорядкованого ряду, стійка до викидів; середнє — сума/кількість, чутливе до викидів.
- **Чому p95?** Хвіст (retry/timeout) ховається в середньому: 90×40 мс + 10×1500 мс дає середнє 186 мс (PASS), p95 = 1500 мс (FAIL).
- **Чому AND, а не зважена сума?** Зважена сума дозволяє компенсувати одну метрику іншою, а AND вимагає балансу.
- **Чи можна «обдурити» Mutation Score?** Складніше, але можливо (еквівалентні мутанти, тести, що дублюють реалізацію), тому він теж не єдиний KPI, а частина gate разом із ревʼю.
